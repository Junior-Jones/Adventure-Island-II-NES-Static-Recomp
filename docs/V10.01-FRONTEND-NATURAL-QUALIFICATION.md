# Version 10.01 — frontend integration and natural runtime qualification

Version 10.01 adds a usable application layer around the existing Adventure Island II static core. The static-core implementation remains Adventure Island II-specific. Mega Man 6 and Battletech C64 were examined only as frontend architecture references and provide no game-specific static execution authority.

## Reference use

Mega Man 6 established the NES-oriented connection pattern used here: exact ROM load/validation, opaque static-core create/reset, a single frame-advance path, controller adaptation, frame copy, and PCM draining after each frame. Battletech C64 supplied application-structure ideas: separate common input/session code, a distinct entry/launcher, headed versus headless organization, deterministic frame limits, capture controls, and final status reporting.

No Mega Man 6 or Battletech game/core implementation was copied into the Adventure Island II static machine. Their source trees remain external reference material and are not packaged as Adventure Island II production authority.

## V10.01 frontend

The project now builds an `ai2-headless` application and, on Linux/X11, an `ai2-linux` headed application. Both use the same `Ai2FrontendSession`, which opens and validates the exact target ROM, creates and resets the opaque Adventure Island II core, advances the same core frame path, copies the 256x240 frame, and drains core-produced PCM.

The headless application supports frame-count or emulated-time limits, repeated exact-frame BMP capture, continuous PCM draining, WAV capture, periodic progress, and a final observation/status record. Emulated seconds are derived from the NTSC NES CPU clock used by the target core rather than wall-clock duration.

The Linux X11 application shares the same session/input adapter. Its keyboard mapping is: arrow keys = D-pad, Z = A, X = B, Enter = Start, Shift = Select, P = pause, Escape = quit. A 60-frame X11 virtual-display smoke run completed with `status=ok`.

## Natural runtime ladder

The final warning-clean build reproduced all requested rungs:

- 300 frames: 8,931,650 total CPU cycles, 2,905,191 statically recompiled instructions, 220,075 PCM samples produced/drained, zero PCM residue, `status=ok`.
- 15-second target: 902 frames, 26,859,511 total CPU cycles, 15.007212647 emulated seconds, 8,706,887 statically recompiled instructions, 661,818 PCM samples produced/drained, zero residue, `status=ok`.
- 90-second target: 5,409 frames, 161,080,238 total CPU cycles, 90.000369321 emulated seconds, 52,185,796 statically recompiled instructions, 3,969,016 PCM samples produced/drained, zero residue, `status=ok`.

These are natural ROM runs through the Adventure Island II static core and frontend. They are validation evidence only and are not used to discover or authorize static code.

## Mesen screenshot differential

Mesen's `endFrame` screenshot callback exposes the just-finished frame buffer one callback later than the native frontend's copy point. After aligning equivalent completed buffers, the final comparison is:

- native frame 299 versus Mesen endFrame 300: 61,395 / 61,440 exact pixels = 99.9267578125%; 45 pixels differ.
- native frame 901 versus Mesen endFrame 902: 61,410 / 61,440 exact pixels = 99.951171875%; 30 pixels differ.
- native frame 5,408 versus Mesen endFrame 5,409: 61,435 / 61,440 exact pixels = 99.9918619792%; 5 pixels differ.

The Mesen core shared library was not modified. The stripped headless launcher had been zero-initializing the NES user palette; the normal Mesen UI supplies a default 2C02 palette. The oracle launcher was corrected to seed Mesen's own canonical 2C02 palette while retaining the exact original Mesen core library. This change affects oracle screenshot presentation only, not Adventure Island II production code.

The WAV contains 3,969,016 samples (90.0003628118 seconds), has peak absolute amplitude 18,324, RMS 6,132.829, is non-silent, and contains zero clipped samples. Its SHA-256 is `f3451523fae7a8077ed639ffa38631fd30e671e6647dff36f565af6f3955510c`.

## Static closure distinction

V10.01 completes the requested frontend integration and natural runtime/screenshot/audio qualification. It does **not** write `STATIC_CORE_COMPLETE`. Starter NES still requires the stricter fresh native/oracle cold-boot differential covering CPU state, important RAM, mapper state, PPU events, and audio timing before the project may claim formal static construction closure. The natural runs and image/audio captures here strengthen runtime confidence but do not waive that gate.
